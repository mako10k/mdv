# Release Work Memo v0.2.1 (release candidate complete, unpublished)

この文書は v0.2.1 release gate evidence の作業中記録である。2026-07-21 終了時点で release candidate は未完成で、tag と GitHub Release は作成していない。

## Scope

- Main-owned rendered-link activation and editor-window navigation hardening.
- Relative, native absolute, and `file:` regular-file links open in MDV; an existing editor for the same tracked path is focused; HTTP(S) uses the existing external-link permission flow.
- Unexpected top-level navigation, renderer new-window requests, invalid or missing local targets, and packaged-renderer `file:` subresources outside application assets are denied.
- Tracked-file watcher failures use bounded backoff and repeated-error log suppression while retaining manual reload fallback.
- Markdown parsing dependencies are updated, and Toast UI Editor's embedded sanitizer instance is rebound to MDV's exact DOMPurify 3.4.12 dependency at build time.

## Dependency Security Preflight

- Initial production audit found 6 findings: 2 high, 3 moderate, and 1 low across `markdown-it`, `linkify-it`, `js-yaml`, `dompurify`, and inheriting packages.
- `markdown-it` resolves to 14.3.0, `linkify-it` to 5.0.2, `js-yaml` to 4.3.0, and DOMPurify to 3.4.12.
- Exact-diff review found that Toast UI Editor 3.2.2 embeds DOMPurify 2.3.3 in its published ESM, so the initial package override and audit result did not change the active sanitizer. Publication was stopped.
- ADR 0026 now requires a fail-closed Vite pre-transform that connects Toast UI's internal `purify` instance to MDV's exact direct DOMPurify dependency and excludes Toast UI from dependency pre-bundling. The transform contract has three release tests.
- The final renderer bundle contains DOMPurify 3.4.12 and no legacy DOMPurify 2.3.3 implementation marker. `npm run build` enforces this output check before packaging.
- The full development and packaging audit still reports 10 findings (1 low, 6 high, 3 critical). The critical `tar` finding is reachable through `electron-builder`, so it remains a build-environment risk but is not shipped in the application runtime. Application source and configuration are repository-controlled, while downloaded Node tooling and lockfile-resolved dependencies remain consciously accepted external build inputs. Final candidate integrity and runtime checks are still required but do not prove that build-tool vulnerabilities were not exercised.
