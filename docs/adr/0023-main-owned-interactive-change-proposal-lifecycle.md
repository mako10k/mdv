# 0023 Main-Owned Interactive Change Proposal Lifecycle

## Status

Accepted

## Context

[`write_target dryRun`](../ai-chat-design.md) already computes a non-mutating active-editor result, but its bounded model-facing preview is not an authoritative user approval surface. Passing complete before/after Markdown through the transcript or generic tool-event JSON would expose document content outside its editor boundary, while applying a renderer-selected patch without rechecking document identity would allow stale or replayed decisions to mutate the wrong state.

Manual hunk editing adds a second authority risk: adding renderer-owned replacement text to final Apply would entangle draft editing, canonical hunk validation, and document mutation in one payload. The proposal needs a separate main-owned revision transition so the final Apply can remain text-free.

This decision extends [ADR 0002](0002-editor-handle-and-span-tool-contract.md)'s dry-run foundation and [ADR 0011](0011-ai-chat-streamed-ipc-contract.md)'s request-correlated stream. It does not supersede either ADR. Save-conflict handling remains governed separately by [ADR 0006](0006-local-file-sync-and-conflict-save.md).

## Decision

- An eligible `write_target(dryRun: true)` invoked from the model tool loop against the live active editor creates an interactive change proposal. Non-dry writes, `:new`, temp-buffer and structure mutations, completed-save conflict handling, snapshot restore, and global suggest mode stay outside this contract.
- The main process owns each transient proposal. It binds an opaque proposal ID to the originating chat request and window, the target editor, one immutable document-instance identity, the exact current path including `null`, the exact baseline Markdown, and stable non-overlapping hunk envelopes derived from the canonical initial diff. Baseline state and envelopes remain immutable; current hunk bodies, proposal revision, and the all-hunks candidate fingerprint are main-owned mutable state.
- Baseline capture and final apply are dedicated typed editor requests. Capture returns document instance, path, and Markdown from one renderer observation. Manual editing uses a separate typed revision IPC carrying one stable hunk ID, revision and fingerprint preconditions, and one canonical LF hunk body. The main process validates and materializes that body, reconstructs the candidate and diff, reapplies the raw-size cap, and atomically increments the revision. Final Apply accepts only a proposal ID, revision and fingerprint preconditions, and selected hunk IDs; the main process derives the resulting Markdown from its current canonical proposal instead of accepting replacement text from the renderer.
- All eligible active-editor dry-run proposal candidates are evaluated ahead of non-candidate siblings from the same model response, preserving order within both groups. This is an intentional approval barrier, not an assumption that sibling calls are independent: no sibling side effect may overtake a candidate that could require user review. The trade-off is that cross-group model order is changed. A candidate that depended on an earlier sibling can therefore fail before that sibling later runs, and it is not retried in the same turn. A failed earlier candidate cannot let a sibling overtake a later candidate. Creating the first proposal terminates that model turn before every remaining candidate, sibling tool call, or further model iteration. Provisional prose from that tool-call iteration is discarded rather than promoted to the final transcript. The bounded model-facing dry-run result may contain proposal status and opaque identity, but full before/after Markdown and authoritative hunks never enter OpenAI input, the chat transcript, generic tool-event JSON, or logs. The transcript permanently states that the proposal-creating turn ended and will not resume automatically; if the request has remaining work, continuation requires a new user message. A later chat turn may consume typed resolution metadata; resolution does not automatically resume the stopped turn.
- The proposal UI uses dedicated typed open, detail, revise-hunk, apply, cancel, and resolution IPC. Receipt of the open summary immediately mounts a loading modal; detail-load failure attempts to cancel the main-owned proposal instead of abandoning it until expiry. If that fallback Cancel is not authoritatively acknowledged, the modal and active proposal identity remain in place with a retryable Cancel error. The modal moves and traps keyboard focus, makes the background workspace inert, rejects background renderer and native menu actions including auxiliary-window actions, and disables window reload roles while a decision is pending. It presents the expiry time and its selection-loss consequence, canonical line hunks defaulted to selected, and per-hunk apply/discard and manual edit controls. Unsaved local drafts and in-flight revisions disable Apply. It states that final Apply consumes the proposal and permanently discards every unselected hunk; saved edits survive selection toggles until that final decision. Cancel writes nothing.
- Hunk revision is an atomic `pending@r -> pending@(r+1)` transition. Cross-window, stale revision or fingerprint, unknown hunk, CR/NUL, baseline no-op, canonicalization failure, and over-limit input fail without changing proposal state or extending its TTL. The main process appends a missing trailing LF to non-empty, non-final envelopes so ordinary textarea replacement cannot merge with the following baseline line. A consistently CRLF baseline sets CRLF materialization; all other baselines use LF. The validated detail is built before committing state; after an IPC error the renderer refetches authoritative detail to distinguish an unchanged retryable draft from a committed revision whose acknowledgement was lost. Raw edited bodies remain on the dedicated proposal IPC and never enter OpenAI input, chat transcript, generic tool events, terminal resolution metadata, or logs.
- Apply is a single-use compare-and-swap transition. The main process validates the current revision and proposal fingerprint, moves `pending -> applying`, composes selected current hunk bodies into the immutable baseline, then the target renderer rechecks document instance, path, and the exact Markdown baseline and applies the main-derived result in the same request handler. Success moves to `applied`; identity or baseline mismatch moves to `stale`; delivery or acknowledgement uncertainty after dispatch moves to `indeterminate` and must not be retried automatically.
- The remaining lifecycle is `pending -> cancelled | invalidated`. Terminal proposals are consumed, and duplicate apply, cancel, or replay is rejected. Window close, renderer loss, expiry, and replacement by a newer proposal invalidate a pending proposal; window close or renderer loss after Apply dispatch makes an applying proposal `indeterminate`. Replacing the document rotates its instance identity, so any later Apply fails closed as `stale` without writing.
- At most one pending proposal exists per editor. Proposals expire after 10 minutes, and the combined raw baseline/current all-hunks candidate Markdown is capped at 2 MiB at creation and after every revision. Ineligible or initially over-limit previews keep the normal bounded dry-run result, including its temp-buffer fallback when truncation or abbreviation requires one, but do not create an interactive proposal.

## Consequences

- Approval is based on a stable main-owned snapshot, while the renderer remains the final authority on whether the same document instance, path, and baseline can still be mutated.
- Stable baseline envelopes preserve hunk identity and selection across line-count-changing edits, but intentionally limit manual editing to the originally proposed hunk boundaries. Replacing a hunk with its baseline is expressed by Discard rather than by a no-op revision.
- Full proposal content requires bounded in-memory lifecycle management and explicit cleanup on terminal state, expiry, renderer loss, and window close. Document replacement rotates identity and leaves the bounded proposal available only for a fail-closed stale decision or expiry.
- A lost acknowledgement cannot be made safe by blind retry; `indeterminate` is intentionally terminal and requires the user to inspect current editor state before requesting a new proposal.
- Candidate-first ordering can leave a compound request partially executed. The UI reports that boundary at proposal creation and resolution; the user must explicitly start a new chat turn for any remaining work.
- Existing non-dry writes and the save-conflict flow keep their current behavior. This contract does not turn them into global suggest-mode writes.
